Projects

Case 01  ·  Deployed, version 1

Homli: trusted PG discovery

My role: Product owner and full-stack developer

Problem
Moving to a new city means piecing a PG together from word of mouth, Maps, listing portals and photos. The facts are scattered, often missing, and photos can mislead.
Goal
Let a newcomer shortlist and compare PGs from facts they can trust, each one labelled with its source.
Research
Started from one friend's real search for a PG, then collected firsthand details and public pages for 11 PGs. No interviews beyond that yet.
Solution
Search by area, PG name, or plain language ("AC under 20k in Bellandur"). Filters, a distance slider, shortlist, compare up to three, and a visit request with duplicate protection.
Results
Deployed end to end with 29 automated tests passing. No usage data yet, since it has not been tested with a wider group.
Assets
Product brief, user flow, state matrix, architecture and API contracts, in the source code repository.

Open the live site ↗ Source code

What I owned

  • Product: problem definition, scope, user flows, state matrix, and the product brief.
  • Backend: REST API in Node and Express, with idempotent bookings, server-side price snapshots and a restricted CORS list.
  • Data: Postgres schema and seed data, with a source recorded for every field. SQLite and in-process Postgres for local use and tests.
  • Search: keyword parser with synonyms and typo tolerance, plus distance filtering using the haversine formula.
  • Quality and delivery: 29 automated tests, deployed on GitHub Pages, Render and Neon.

Product decisions

  • Unknown details are never guessed. The page says "Details being verified".
  • No scraping and no invented reviews. Photos are used with permission and credited.
  • The Google API key stays on the server.

Scope and limits

A prototype with 11 PGs, from firsthand information and public pages. Booking is a demo: nothing is sent to a PG. I directed the build with an AI coding assistant (Claude Code), and tested and deployed it myself. The problem comes from one user's experience and is not yet validated at scale.

Case 02  ·  In development

Aptitude practice game

My role: Product owner and developer

Problem. Aptitude preparation is repetitive and hard to stick to: open a question bank, solve MCQs, see a score, leave.

Approach. A game with six aptitude tracks, short levels, interactive question types instead of only MCQs, a daily challenge with a streak, and concept mastery computed from real answers. The first version covers two genres of 10 levels each, with stars, XP and coins.

Status: product brief written and the build is under way. The problem is a hypothesis and has not been tested with users yet.
